# UNR Changelog

为 Flutter 小说阅读器 UNR 编写 `CHANGELOG.md`，保留已发布版本的记录。参考 MAA skill 的净变更整理方法，但采用 UNR 的 `dev → master → 版本标签 → Release 草稿` 流程。

## 确认版本与范围

1. 在包含本 skill 的 UNR 仓库根目录工作，先检查工作区、当前分支、`pubspec.yaml`、已有 `CHANGELOG.md`、版本标签及 `.github/workflows/release*.yml`。用户指定其他 checkout 时，先核对其项目身份与发布流程。
2. 目标版本从用户明确输入、Release PR/CI 提供的版本或 `pubspec.yaml` 获取。`version: X.Y.Z+构建号` 的日志标题只使用 `vX.Y.Z`，保留预发布后缀。不要根据旧 tag 猜测新版本，也不要自动递增版本号。输入与 pubspec 不一致时先核对用途；发版准备必须一致。
3. 确认基线和结束提交：普通版本相对上一次已发布版本；预发布版本相对直接前驱预发布版；正式版要涵盖上一次正式版之后的有效变化。tag 用于定位历史边界，不能证明其对应 Release 已发布；必要时只读查看 Release 状态。用户指定范围时优先采用，无法确定且影响内容时询问。
4. 当前目标 tag 已存在时，区分补写历史记录与准备新版本；后者先取得明确的新版本号，不覆盖已发布版本、移动 tag 或伪装成一次新发布。没有历史日志时只创建已确认的版本内容，不编造过去版本。

在 Windows 上读取 Git 历史时使用 UTF-8，例如：

```powershell
git -c i18n.logOutputEncoding=utf-8 log --encoding=UTF-8 --format="%H%x09%an%x09%ae%x09%s" BASE..HEAD
git diff --stat BASE..HEAD
git diff BASE..HEAD -- lib android windows pubspec.yaml .github
```

将 `BASE`、`HEAD` 换成已核对的引用；不要对已经正确解码的中文再做系统编码转换。

## 整理净变化

* 以最终功能和用户可感知效果为准。同一问题的多次修正、review 修改和后续回归修复合并为一条；完全撤销的改动省略，部分撤销保留最终结果。
* 标题含糊、口语化或只描述实现时查看 diff，改写成读者能理解的效果。功能若仅适用于 Android、Windows、某平台或某种登录方式，写清条件。不能把模拟器验证写成全部平台已验证。
* 纯版本号更新、更新日志提交、格式整理和无产品收益的内部维护通常省略；`chore`、`perf` 不机械过滤，有性能、启动、稳定性或体验收益时保留。尊重 `[skip changelog]`，若实际重要行为与标记矛盾，先核对。
* 用有内容的分类：`### 新增 | New`、`### 改进 | Improved`、`### 修复 | Fix`；必要时补 `### 文档 | Docs` 或 `### 其他 | Other`。分类依据实际变化，不直接照搬 commit type。同一效果只放在一个分类，优先排列主要功能和兼容性变化。
* 默认写中文，列表用 `*`，中英文和数字间留空格，保留 EPUB、TXT、Flutter、Android、Windows、ADB 等正式写法。不要复制 MAA 的服务器、MaaMacGui、术语映射或作者名单。
* 已核实的 PR 保留链接，作者按 `%an` 与 PR 发起人/协作者核实，不使用 `%cn` 当贡献者。`@作者` 只使用确认的 GitHub login；无法确认时保留真实作者名或省略署名，不猜用户名、不公开邮箱。

## 版本内容与历史

文件使用以下边界，便于 CI 精确提取当前版本：

```markdown
# 更新日志

## vX.Y.Z

### 亮点

* 本版本最值得强调的变化。

### 新增 | New

* 已核实的新增能力。

### 修复 | Fix

* 已核实的问题修复。

## v上一版本

保留原有内容。
```

* 每个版本只有一个 `## v版本号` 标题，最新版本在最上方，标题不带构建号或日期；分类使用三级标题。不要使用 MAA 的 `<details>` 版本折叠块，或把版本标题放在代码围栏中。
* 亮点是可选项：少量重要变化才值得强调，没有足够内容时省略。英文版只在用户要求时添加。
* 正式版从预发布版晋升时，优先汇总同一目标版本已有的预发布日志、跨版本去重并保留最终表述，再分析最后一个预发布 tag 之后的增量。保留已整理过的亮点；最终 diff 出现撤销或矛盾时针对该项复核。已有预发布日志不完整时再补充所需历史，不机械重写所有内容。
* 普通版本与预发布版本只写当前范围的增量。历史条目保持不动，不因为跨次版本就删除 UNR 的旧日志；正式版汇总预发布变化不意味着删除已发布预发布版的历史记录。
* 模板只用于说明格式；实际文件中不能留下 `X.Y.Z`、`TODO`、待补充或虚构条目。没有有效变化时说明实际情况，不用占位内容通过检查。

## 写入、提交与发布衔接

* 用户只要正文时输出最终 Markdown；要求更新文件或准备发版时实际编辑 `CHANGELOG.md`，交付范围说明和验证结果。
* 项目将 `CHANGELOG.md` 作为发布记录；README 继续只放开源库与声明，草稿材料放 `.local/`，不提交额外发布文档。
* 更新日志和目标 `pubspec.yaml` 版本应在 `dev` 的发版准备阶段提交。先运行 `python .github/scripts/release.py changelog` 与 `git diff --check`，检查差异；沿用中文约定式提交，例如 `docs(changelog): 整理 vX.Y.Z 更新日志`。只暂存本任务相关文件，不混入他人改动。
* `Release Preparation` 检查 `dev → master` PR 的版本与日志。检查失败时补充 changelog commit 并推送原 `dev`，不需要关闭或重建 PR。检查通过后合并，标签必须指向已包含版本号和日志提交的 `master` 提交。
* `Release` 的 metadata job 在构建前验证当前版本日志。草稿正文取自标签对应提交的当前版本区块；重跑保留维护者已编辑的草稿说明，不覆盖已发布 Release。
* 单纯整理日志不会自动推送、创建 PR、打标签或发布。只执行用户已授权的步骤；若用户还未授权下一步，先完成可审阅文件与本地验证，再说明具体操作。

交付前检查：版本来源与边界明确，净变化合并，无重复/撤销/虚构项，当前内容不混入历史，平台限定真实，PR 和作者归属有依据，日志校验通过。
