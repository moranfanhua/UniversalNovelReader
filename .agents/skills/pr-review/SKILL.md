# UNR PR 交叉审查

用两个独立子智能体覆盖同一份 PR。首轮独立找问题，第二轮互相验证，主智能体根据证据裁决；两者意见一致不等于问题已证实，只有一方发现也不构成排除理由。

## 固定审查范围

1. 检查工作区、当前分支和仓库身份，读取适用的 `AGENTS.md`。从用户提供的 PR 链接或编号获取正文、base/head SHA、完整改动文件列表和 diff；编号按当前仓库解析，不猜测目标 PR。
2. 为本轮固定同一个 head SHA、base SHA 和 merge-base，两个子智能体使用同一份比较范围。区分 PR 提交与本地未提交内容；优先用 `git show`、`git diff` 或只读 GitHub 工具读指定版本，不覆盖当前工作区或切换用户正在使用的分支。
3. 阅读相关实现、调用链和现有回归测试，不能仅凭 PR 描述、提交标题或 CI 通过判断正确性。说明是否存在无法取得的文件、截断的 diff 或其他覆盖限制。

## 第一轮：两个独立审查

* 必须实际启动两个子智能体，例如命名为 `reviewer_a` 和 `reviewer_b`，不再嵌套委派。使用可用的子智能体工具，不创建新的用户聊天来替代子智能体。
* 两者都审查完整的同一范围，不把文件对半分配。可以采用不同检查顺序，但都需检查正确性、行为回归和相关测试是否真正覆盖风险。
* 首轮只提供原始上下文：仓库位置、PR 原始需求、固定 SHA、适用规则和取证方式。不提供主智能体、另一子智能体或已有评论的候选结论。工具支持时使用不继承聊天历史的方式，例如 `fork_turns="none"`，并要求自行读取项目规则。
* 两者使用独立上下文，但可能共享文件系统；禁止并行修改项目文件。默认沿用当前模型与推理设置，不擅自为审查指定另一模型。
* 每个候选问题需给出：对应改动行、具体触发条件、相关代码路径、用户可见影响、证据或反例、建议严重程度和未验证项。没有发现问题时如实返回，不为满足数量凑问题。
* 主智能体等待两份初步结果齐备后再进入第二轮。期间可独立核对事实，不把尚未核实的猜测提前发送给任何一方。

可用下面的任务骨架分别委派；将方括号内容替换成已核实信息：

```text
独立审查 UNR PR [链接]，仓库位于 [目录]。
固定范围：base=[SHA]，head=[SHA]，merge-base=[SHA]。
先读取项目 AGENTS.md，再审查完整 diff、相关实现及回归测试。
只返回有依据的候选缺陷、反例和覆盖限制；不要修改项目、发布评论或创建子智能体。
完成前不要查看其他审查者的结论。每项注明触发条件、影响、文件行号和验证情况。
```

## 第二轮：交换候选问题

1. 保留两份首轮结果，将 A 的候选问题交给 B、B 的交给 A；通过后续任务唤醒原有两者，不另开第三个审查子智能体。若双方均无候选问题，仍要求核对彼此的覆盖范围和遗漏风险。
2. 要求逐项尝试证实或推翻，检查实际可达性、已有保护、版本差异和相关测试。返回“证实 / 排除 / 证据不足”及依据，不仅给出赞同或反对。
3. 主智能体等待两份交叉核验结果，再亲自复核候选问题与分歧，按触发条件和代码证据裁决、合并重复项。区分本 PR 引入或加剧的问题与已有问题；不把已有问题冒充本 PR 的缺陷。
4. 需要复现时运行最小相关检查，遵守项目的设备、真实账号和写操作约定。无法验证真实账号交互时明确限制，不能用 mock 或构建成功代替。

## 汇总与边界

* 交付前核对 PR head 是否变化。有新提交时让原有两者补审受影响范围；尚未补审的提交明确列为未覆盖，不能把旧结果表述为最新版本已通过。
* 按严重程度排列已核实问题，附准确文件行号、触发条件、影响和验证依据。明确两轮审查是否完成、关键分歧如何处理，以及未运行或无法完成的验证。证据不足的线索单独说明，不写成确定缺陷。
* 没有发现可确认问题时直接说明，并保留实际覆盖限制；不能承诺没有缺陷。
* 本地文件使用绝对路径 Markdown 链接；PR 改动优先使用当前 diff 的准确行号链接。不能根据函数名猜行号。
* 默认只审查，不修改代码、提交或向 GitHub 发布评论。用户已明确授权后续修复或发布时执行相应步骤；修复后的新提交需要重新核对受影响范围。
* 子智能体工具不可用、额度不足或一方失败时，说明缺失的步骤和覆盖范围；不能把主智能体自己的两次分析当成两个独立子智能体的结果。
